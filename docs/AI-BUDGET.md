## 1. 무엇이 분량을 키웠나

측정 전의 짐작과 달랐습니다. **도구 결과는 문제가 아니었습니다** — 이미 8건 상한과 요약 JSON 이라 한 번에
2,000자 안팎이었습니다. 분량은 두 곳에서 나왔습니다.

1. **챗봇이 왕복마다 대화 전체를 다시 싣습니다.** 도구를 부를 때마다 모델을 다시 부르고, 그때마다 대화 기록
   (입력 검증의 최대 24턴 × 4,000자 = 96,000자)과 시스템 프롬프트·도구 선언을 처음부터 보냅니다. 8번이면
   8배입니다.
2. **리뷰 요약이 같은 그림을 리뷰마다 다시 붙였습니다.** 이모티콘만 쓴 리뷰는 그림을 봐야 뜻을 알 수 있어
   파일을 base64 로 붙이는데, 인기 이모티콘(913KB · 118KB GIF)을 리뷰 40개가 쓰면 같은 그림이 40번 갑니다.
   리뷰 수 상한도 없어 300개 본문(9만 자)을 전부 실었습니다.

## 2. 상한 — 어디에 무엇이

| 상한 | 값 | 위치 | 넘으면 |
|---|---|---|---|
| 대화 기록 | 12,000자 | `lib/chat-budget.ts` `HISTORY_CHAR_BUDGET` | 최근 것부터 채우고 앞쪽을 뺍니다. 마지막 질문은 늘 남고, 뺀 수를 맨 앞에 한 줄로 알립니다(모델이 "아까 그 오락실" 을 지어내지 않게) |
| 도구 결과 누적 | 12,000자 | `lib/chat-budget.ts` `TOOL_OUTPUT_CHAR_BUDGET` | 다음 왕복에서 함수 호출을 막아 찾은 데까지로 답합니다 |
| 왕복 | 8번 | `app/api/chat/route.ts` `MAX_ITERATIONS` (기존) | 마지막 왕복은 함수 호출을 막습니다 |
| 도구 한 쪽 | 5건 · 20쪽까지 | `lib/chat-tools.ts` `PAGE_SIZE` · `MAX_PAGE` | 결과의 `hasMore` 가 true 면 모델이 `page` 를 올려 다음 쪽을 부릅니다 |
| 요약 리뷰 수 | 최근 60개 | `lib/review-summary-types.ts` `REVIEW_SUMMARY_MAX_REVIEWS` | 오래된 리뷰는 요약에 안 들어갑니다 — 화면이 "최근 후기 N개 기준 (전체 M개)" 로 밝힙니다 |
| 요약 본문 | 15,000자 | `REVIEW_SUMMARY_CHAR_BUDGET` | 넘기 전에서 멈춥니다(첫 리뷰는 길어도 넣음) |
| 요약 그림 | 서로 다른 4장 | `REVIEW_SUMMARY_MAX_IMAGES` | 같은 그림은 한 번만. 다시 나오면 "앞에 붙인 그림과 같습니다", 상한 밖은 이름만 |

운영 로그 — 요청 하나가 실제로 쓴 토큰을 남깁니다(본문은 남기지 않습니다). 모양은 이렇습니다:

```
[chat] 토큰 입력 N · 출력 N · 생각 N · 도구 N · 합 N (모델 N번 · 도구 결과 N자 · 대화 N턴 · 앞 N턴 생략)
[review-summary] arcade 42: 리뷰 54/300개 · 그림 2장 → gemini-3.7-flash      ← 위 측정의 인기 오락실
```

## 3. 쪽 나누기는 DB 에서 — 오락실 도구

예전 오락실 도구는 `listArcades` 로 조건에 맞는 곳을 **전부** 받아 앞의 8곳만 썼습니다. 그 SQL 은 오락실마다
보유 기종·기체·컨디션을 집계하므로, 기종 하나로 찾으면 목표 규모에서 926곳을 집계한 뒤 918곳을 버렸습니다.

지금은 두 번에 나눕니다 (`lib/arcades.ts` `pageArcades`):

1. `prisma/sql/arcadeSearchPage.sql` — 같은 조건으로 **그 쪽의 id 와 전체 수만** 고릅니다 (집계 없음)
2. `prisma/sql/arcadesWithMachines.sql` — 그 id 들만 집계합니다 (새 조건 `$7 ids` — 빈 배열이면 필터 없음)

한 SQL 안에서 자르는 방법 둘을 먼저 해 보고 버렸습니다. 지도 목록(`/api/arcades`)이 모든 방문에서 부르는
쿼리라, 거기가 느려지면 챗봇이 빨라진 것보다 손해입니다. EXPLAIN (ANALYZE) 실행 중앙값, 목표 규모:

| 방법 | 지도 목록 (926곳) | 반경 5km (30곳) | 판단 |
|---|---:|---:|---|
| 원래 SQL | 20.8ms | 1.42ms | 기준 |
| base 에 창 함수 · 정렬 · LIMIT | 23.2ms (+2.4) | 1.54ms | 버림 — 전체 목록에 정렬·세기가 붙습니다 |
| UNION 두 갈래 (limit 있을 때만 정렬) | 22.4ms (+1.6) | **3.01ms** | 버림 — 행 수 추정이 바뀌어 `cabinet_condition` 뷰를 통째로 해시 조인했습니다 |
| **id 조건 하나 + 쪽 고르는 SQL 따로** | 21.2ms (+0.3) | 1.50ms | 채택 — 세 번 잰 값끼리의 폭(원래 SQL 20.4~21.7ms) 안 |

각 칸은 7번 실행(앞 2번 버림)의 중앙값을 세 번 잰 것의 가운데 값입니다. 쪽 하나(5곳)를 집계하는 두 번째 SQL 은
0.92ms 입니다.

대신 조건이 두 파일에 있습니다. 두 파일의 `-- ▼ 조건` ~ `-- ▲ 조건` 블록은 **글자까지 같아야** 하고
`tests/typed-sql.test.ts` 가 대조합니다 — 한쪽만 고치면 챗봇이 "강남에 3곳" 이라 하는데 지도에는 4곳이 뜹니다.

## 4. 늘어난 것 · 남은 것

- **보통 질문은 6.3% 늘었습니다** (6,939 → 7,373자). 도구 선언 셋에 `page` 칸이 붙었고, 선언은 왕복마다
  실립니다. 설명을 줄여 8.8% 에서 6.3% 로 낮췄습니다. 긴 대화·많은 도구 호출에서 줄어드는 양(−81%)과
  바꾼 값입니다.
- 오락실 도구의 SQL 이 1 → 2 문장입니다 (쪽 고르기 + 집계). 앱과 DB 가 한 장비라 왕복 하나는 ~0.1ms 입니다.
- 리뷰 요약은 **최근 리뷰만** 읽습니다. 오래된 리뷰의 내용은 요약에 들어가지 않습니다 — 기체 상태처럼 최근이
  더 맞는 정보라서 그쪽을 골랐고, 화면에 몇 개를 읽었는지 적습니다. 저장하는 `review_count` 는 여전히 전체
  수라, 리뷰가 하나 늘면 요약이 다시 만들어집니다(상한이 있어 매번 같은 분량).
- 실제 토큰 수는 재지 않았습니다(외부 호출 없음). 운영에서 `[chat] 토큰` 로그로 확인하세요.
- 그대로 둔 것 — 게시글 검색의 한글 2글자(Seq Scan, DB-WORKLOAD §2.7) · 리뷰 목록 API
  (`/api/arcades/:id/reviews`)는 여전히 전부를 돌려주고 화면이 쪽을 나눠 그립니다. 리뷰가 수백 개가 되는
  오락실이 생기면 서버 쪽 쪽 나누기가 다음 후보입니다.
