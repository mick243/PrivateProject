# 디자인 · UX 라이팅 지침서

> 2026-09-29 작성. **사람이 읽는 모든 것**에 적용합니다 — 화면 · 버튼 · 안내문 · 빈 화면 ·
> 오류 문구(서버가 돌려주는 `error` 도 화면에 그대로 뜹니다) · 메일 · 챗봇 답변 말투.
> 성능 · 보안 · API 규칙은 [../GUIDELINES.md](../GUIDELINES.md) 가 정본입니다.
>
> 뿌리는 아래 §1 의 디자인 철학 4가지와 §2 의 라이팅 원칙 8가지입니다. 원칙은 원문 그대로 두고,
> 그 아래에 **이 프로젝트에서 무엇을 뜻하는지**와 **지킬 규칙**을 붙였습니다. 규칙은 코드 리뷰에서
> 예/아니오로 가를 수 있게 썼습니다.

## 0. 30초 요약

1. **한 화면에는 질문 하나, 주 버튼 하나.** 보조 행동은 글자 링크로 낮춥니다.
2. **문장은 모두 해요체.** 버튼은 누르면 무엇이 되는지를 동사로 씁니다 (`리뷰 남기기`, `가입하기`).
3. **오류는 탓하지 않고 다음에 할 일을 말합니다.** "잘못된 · 올바르지 않습니다 · 실패" 를 쓰지 않습니다.
4. **어려운 말은 쉬운 말로.** 기종 → 게임, 기체 → 기계, 반경 → 거리 (§5 사전).
5. **숫자는 맥락과 함께.** "제보 1/3" 이 아니라 "2명이 더 알려 주면 바로 반영돼요".

## 1. 핵심 디자인 철학 (Design Principles)

### 1-1. 본능적인 직관성 (Intuitive Simplicity)

> 설명이 필요 없는 디자인을 지향합니다. 깨끗하고 단정한 인터페이스를 통해 사용자가 학습 없이도
> 본능적이고 자연스럽게 서비스를 이용하도록 합니다.

**이 프로젝트에서** — 폼 위에 설명 문단을 깔지 않습니다. 칸의 이름이 곧 설명이어야 합니다.

- [ ] 입력 칸 위에 "이 화면은 ~하는 곳입니다" 류의 설명 문단을 두지 않는다. 꼭 필요한 도움말은 **칸 아래 한 줄**.
- [ ] **할 수 없는 일은 보여 주지 않는다.** 관리자 전용 단추를 일반 사용자에게 "관리자만" 이라는 글로 알리지 않는다.
- [ ] 아이콘만 있는 단추에는 `aria-label` 과 `title` 을 단다 (§3-6).
- [ ] 한 화면의 안내문은 **두 문장까지**. 세 문장이 필요하면 화면을 나눈다.

### 1-2. 1화면 1행동 (One Screen, One Action)

> 한 화면(페이지)에서는 사용자에게 단 '하나의 질문' 또는 '하나의 핵심 행동'만 요구합니다.
> 불필요한 정보와 선택지를 과감히 제거하여 인지 부하(Cognitive Load)를 최소화합니다.

**이 프로젝트에서** — "화면" 은 페이지뿐 아니라 **열려 있는 패널 · 카드 · 폼** 하나하나입니다.

- [ ] 화면(열린 패널 · 카드)마다 `btn-primary` 는 **하나**.
- [ ] 보조 행동(취소 · 다른 길 · 나중에)은 `.btn-link` 글자 링크로 낮춘다. 주 버튼과 같은 무게로 나란히 두지 않는다.
- [ ] 질문이 여럿 필요한 흐름은 **단계로 나눈다** — 가입은 아이디 → 이메일 → 비밀번호 → 동의 4단계 (`SignupForm`).
- [ ] 한 번에 **입력 창 하나만** 열린다 — 제보 폼은 하나를 열면 다른 것이 닫힌다 (`ArcadeDetailPanel`).
- [ ] 되돌릴 수 없는 행동(탈퇴 · 지우기)은 주 행동과 같은 줄에 두지 않는다. 설정 화면은 **목록에서 하나를 골라 들어가는** 모양 (`AccountForm`).

### 1-3. 파격적인 도전 정신 (Radical Convenience)

> 기존 보수적인 서비스의 틀과 관습을 깹니다. 과거 사용자가 겪었던 지루하고 불편한 경험을 놀라울
> 정도로 쉬운 편의성으로 전환합니다.

**이 프로젝트에서** — "원래 그렇게 하니까" 로 남아 있는 단계를 지웁니다.

- [ ] 알고 있는 값은 먼저 채운다 — 소셜 계정의 이름, 돌아갈 화면(`?next=`), 마지막 위치.
- [ ] 한 번이면 될 일을 두 번 시키지 않는다 — 가입이 끝나면 곧바로 로그인된 채 보던 화면으로.
- [ ] **막힌 화면에는 풀어 줄 단추를 둔다.** 빈 결과 · 오류 · 한도 초과마다 "다음에 누를 것" 이 하나 있어야 한다.
- [ ] 버튼 문구에 고른 값을 담는다 — `대기 2명으로 알리기`. 누르기 전에 결과가 보인다.

### 1-4. 사용자 중심의 공감 (User-Centric Empathy)

> 권위적인 언어를 버리고, 사용자 입장에서 가장 쉽고 매끄러운 동선을 설계합니다.

**이 프로젝트에서** — 시스템의 사정이 아니라 사람이 할 수 있는 일을 말합니다.

- [ ] 금지 표현: `~은 필수입니다` · `~해야 합니다` · `불가합니다` · `허용되지 않습니다` · `잘못된` · `올바르지 않습니다` · `실패했습니다` · `관리자에게 문의하세요`.
- [ ] 시스템 내부 사정(설정 키 · 모델 이름 · 테이블 이름)을 일반 사용자 화면에 내지 않는다. 개발자에게 필요한 안내는 개발 모드에서만 (§6).
- [ ] 거절할 때는 **대신 할 수 있는 것**을 함께 준다 — "자유 질문은 로그인하면 답해 드려요. 오락실 찾기는 지금 바로 돼요."

## 2. UX 라이팅 8가지 원칙 (Writing Principles)

각 원칙 아래 표는 **이 프로젝트에서 실제로 고친 문장**입니다 (2026-09-29).

### 2-1. 쉬운 용어 쓰기 (Easy Terms)

> 어려운 금융·기술 전문 용어를 지양하고, 초등학생도 이해할 수 있는 쉬운 일상 언어로 대체합니다.

- [ ] §5 쉬운 말 사전을 따른다. 사전에 없는 새 용어는 사전에 먼저 넣는다.
- [ ] `id` · `JSON` · `파싱` · `세션` · `API` · `SDK` · `키` 는 사용자 문구에 쓰지 않는다.

| 전 | 후 |
|---|---|
| JSON 본문을 파싱할 수 없습니다 | 보낸 내용을 읽지 못했어요. 새로고침한 뒤 다시 시도해 주세요 |
| 수렴도가 0.6 미만 — 사람마다 체감이 크게 갈리는 채보입니다 | 의견이 크게 갈리는 채보예요. 의견 일치도가 0.6보다 낮으면 '개인차' 칸에 놓여요 |
| 선택한 기종을 모두 보유한 곳만 표시됩니다 | 고른 게임이 모두 있는 곳만 보여 드려요 |

### 2-2. 친근한 어조 유지하기 (Friendly Tone)

> 격식 차린 딱딱한 말투 대신, 옆에서 친절한 동료나 친구가 안내하듯 자연스럽고 따뜻한
> 톤앤매너(~해요, ~할까요?)를 사용합니다.

- [ ] 문장은 해요체. `~합니다` · `~하시겠습니까?` · `~바랍니다` 를 쓰지 않는다.
- [ ] 과한 존대(`~하시면 ~해 드리겠습니다`)도 줄인다 — `~하면 ~해 드려요`.

| 전 | 후 |
|---|---|
| 이미 로그인되어 있습니다 | 이미 로그인했어요 |
| 정말 탈퇴할까요? … 되돌릴 수 없습니다 | 정말 탈퇴할까요? … 되돌릴 수 없어요 |

### 2-3. 명확한 메시지 전달하기 (Clarity)

> 애매모호한 표현을 배제하고, 사용자가 지금 무엇을 해야 하는지, 다음 단계에서 어떤 일이
> 일어나는지 명확히 알립니다.

- [ ] 안내문에는 **지금 할 일** 또는 **다음에 일어날 일** 중 하나가 반드시 들어 있다.
- [ ] 단계가 있는 흐름은 몇 단계 중 몇 번째인지 보인다 (`1/4`).

| 전 | 후 |
|---|---|
| 제보가 등록되었습니다. 감사합니다! | 알려 줘서 고마워요! 다음 사람이 바로 볼 수 있어요 |
| 해제 | 기준 위치 지우기 |

### 2-4. 간결하게 핵심만 말하기 (Conciseness)

> 불필요한 미사여구와 중복되는 표현을 덜어내고, 꼭 필요한 핵심 정보만 짧게 전달합니다.

- [ ] 안내문 두 문장 이내, 버튼 12자 이내(값이 들어가는 버튼은 16자).
- [ ] 같은 말을 제목과 본문에 되풀이하지 않는다.

| 전 | 후 |
|---|---|
| 둘러보기와 제보·글쓰기는 로그인 없이도 됩니다. 로그인하면 남긴 글이 한 계정에 모이고, 오락실 정보 수정·삭제는 관리자만 할 수 있습니다. | (지움 — 로그인 화면의 일은 로그인 하나) |

### 2-5. 긍정적인 경험 제공하기 (Positive Experience)

> 경고나 오류 상황에서도 사용자를 탓하거나 불안감을 주지 않으며, 해결 방안 중심의 긍정적인
> 문장을 구성합니다.

- [ ] 오류 = **[무슨 일이 있었는지] + [어떻게 하면 되는지]**. 앞은 짧게, 뒤를 구체적으로.
- [ ] 사용자의 실수처럼 들리는 말(`잘못 입력`)을 쓰지 않는다. 조건을 알려 준다(`2자 이상으로 써 주세요`).
- [ ] "실패" 대신 "~하지 못했어요".

| 전 | 후 |
|---|---|
| 아이디 또는 비밀번호가 올바르지 않습니다 | 아이디나 비밀번호가 맞지 않아요. 다시 확인해 주세요 |
| 네트워크 오류 | 연결이 잠깐 끊겼어요. 다시 시도해 주세요 |
| 이메일 형식이 올바르지 않습니다 | 이메일 주소를 다시 확인해 주세요 (예: you@example.com) |

### 2-6. 일관성 있는 톤앤매너 (Consistency)

> 버튼, 타이틀, 안내 문구 전체에 걸쳐 동일한 호칭과 일관된 어조를 유지합니다.

- [ ] 같은 동작은 어느 화면에서든 같은 말 — 지우기는 늘 `지우기`, 저장은 늘 `저장하기`.
- [ ] §3 의 호칭 · 어미 · 문장부호 규칙을 따른다.
- [ ] 같은 개념은 §5 사전의 한 단어만 쓴다 (`컨디션` 과 `상태` 를 섞지 않는다).

### 2-7. 사용자 행동 유도하기 (Action-Oriented)

> 버튼(CTA) 문구는 단순히 '확인', '다음'이 아니라, 클릭 후 어떤 결과를 얻게 되는지 직관적인
> 행동 언어(예: '3초 만에 송금하기', '혜택 받기')로 작성합니다.

- [ ] 주 버튼 단독 금지어: `확인` · `다음` · `제출` · `등록` · `완료` · `예` · `아니오`.
- [ ] 주 버튼은 `[대상] [동사]하기` — `리뷰 남기기` · `글 올리기` · `이 아이디로 할게요`.
- [ ] `닫기` · `취소` 는 보조 행동(글자 링크 · 대화상자)에만.

| 전 | 후 |
|---|---|
| 로그인 / 회원가입 / 취소 (같은 무게 셋) | **로그인하기** · 처음이라면 가입하기(링크) |
| 제보 | 이 게임 있어요 알리기 |
| 등록 (리뷰) | 리뷰 남기기 |

### 2-8. 데이터 기반의 공감 (Data & Context)

> 사용자의 현재 상황, 맥락, 데이터 스토리에 맞춘 구체적인 메시지로 높은 공감대를 형성합니다.

- [ ] 알고 있는 숫자는 문장에 넣는다 — 남은 인원, 남은 시간, 결과 수.
- [ ] 모르는 값은 비워 두지 않고 "아직 몰라요" 라고 쓴다 (빈칸은 "좋다" 로 읽힌다).
- [ ] 사람 이름 · 오락실 이름이 있으면 부른다 — `'홍대 게임랜드' 주변을 보고 있어요`.

| 전 | 후 |
|---|---|
| 제보 1/3 — 3명이 모이면 자동 반영됩니다 | 알려 줘서 고마워요! 2명이 더 알려 주면 바로 반영돼요 |
| 시도가 너무 많습니다. 15분 뒤에 다시 해 주세요 | 여러 번 틀려서 잠깐 잠갔어요. 15분 뒤에 다시 시도해 주세요 |

## 3. 문장 규칙

### 3-1. 어미

| 자리 | 규칙 | 예 |
|---|---|---|
| 안내 · 오류 · 빈 화면 · 성공 | 해요체 문장 | 아직 리뷰가 없어요 |
| 제목(h1 · h2) | 명사구, 또는 한 가지를 묻는 질문 | 로그인 · 어떤 아이디를 쓸까요? |
| 주 버튼 | `~하기` · 결과가 보이는 동사 | 가입하기 · 리뷰 남기기 |
| 보조 링크 · 작은 버튼 | 짧은 동사 | 닫기 · 지우기 · 수정 |
| 진행 중 표시 | `~하는 중…` (말줄임표는 `…` 한 글자) | 저장하는 중… |
| 라벨(칸 이름 · 표 머리) | 명사 | 아이디 · 투표 수 |

### 3-2. 호칭

- **사용자를 부르는 대명사를 쓰지 않습니다** (`당신` · `회원님` · `고객님` 없음).
- 사용자 자신의 것은 `내 ~` — 내 위치 · 내 리뷰 · 내 정보.
- 서비스는 스스로를 부르지 않습니다 (`저희` 없음). 서비스 이름이 필요하면 `오락실 파인더`.
- 관리자는 `관리자`.

### 3-3. 문장부호와 표기

- 느낌표는 **고마움 · 성공**에만, 한 화면에 하나까지.
- 따옴표로 사용자가 적은 말이나 이름을 감쌀 때는 `'…'`.
- 숫자와 단위는 붙인다 (`3명` · `5km` · `24시간`). 천 단위 쉼표 (`29,178곡`).
- 가운뎃점 `·` 은 나란한 항목에만. 문장을 잇는 데 쓰지 않는다.

### 3-4. 길이

- 안내문 두 문장, 한 문장 40자 안팎.
- 주 버튼 12자 이내 (값이 들어가면 16자).
- 오류 문구는 "무슨 일" 한 마디 + "할 일" 한 마디.

### 3-5. 시각 위계

| 역할 | 클래스 | 한 화면에 |
|---|---|---|
| 주 행동 | `btn btn-primary` (폼 카드에서는 `btn-block` 으로 가로를 채움) | 1개 |
| 나란한 보조 행동 | `btn` | 필요한 만큼 |
| 낮춘 보조 행동(취소 · 다른 길 · 나중에) | `btn-link` | 필요한 만큼 |
| 되돌릴 수 없는 행동 | `btn btn-danger` — 주 행동과 다른 줄 | 1개 |
| 단계 표시 | `.steps` (`1/4` · 막대) | — |

### 3-6. 접근성 문구

- 아이콘 단추의 `aria-label` 은 **동사구** — `즐겨찾기에 담기` · `메뉴 열기`.
- 상태가 바뀌는 토글은 지금 상태가 아니라 **누르면 일어날 일**을 적는다.
- `title` 은 `aria-label` 과 같은 말이거나 한 걸음 더 구체적인 말.

## 4. 패턴 사전

| 상황 | 틀 | 예 |
|---|---|---|
| 빈 화면 | [아직 없어요] + [채우는 방법 또는 단추] | 아직 리뷰가 없어요. 다녀왔다면 첫 리뷰를 남겨 주세요 |
| 검색 결과 없음 | ['검색어'가 없어요] + [넓히는 방법] | '홍대 펌프' 에 맞는 오락실이 없어요. 게임 고르기를 풀어 보세요 |
| 오류(일반) | [~하지 못했어요] + [다시 시도해 주세요] | 목록을 불러오지 못했어요. 다시 시도해 주세요 |
| 연결 끊김 | 고정 문구 | 연결이 잠깐 끊겼어요. 다시 시도해 주세요 |
| 서버 오류(500) | 고정 문구 | 잠깐 문제가 생겼어요. 조금 뒤에 다시 시도해 주세요 |
| 없는 대상(404) | [~을 찾을 수 없어요] + [이유 짐작] | 글을 찾을 수 없어요. 지워졌을 수 있어요 |
| 로그인 필요 | [로그인하면 ~할 수 있어요] + 로그인 링크 | 로그인하면 리뷰를 남길 수 있어요 |
| 한도 · 잠금 | [무엇을 다 썼어요 / 잠깐 잠갔어요] + [언제 다시] | 오늘 AI 검색을 다 썼어요. 5시간 뒤에 다시 열려요 |
| 입력 조건 | [칸]은 [조건]으로 써 주세요 | 아이디는 2~20자로, 띄어쓰기 없이 써 주세요 |
| 되돌릴 수 없는 확인 | [대상]을 지울까요? + [결과]. 되돌릴 수 없어요 | 이 글을 지울까요? 댓글도 함께 지워지고 되돌릴 수 없어요 |
| 성공 | [~했어요] (+ 다음에 일어날 일) | 저장했어요 |
| 진행 중 | [~하는 중…] | 불러오는 중… |
| 권한 없음(403) | [~만 할 수 있어요] | 내가 쓴 글만 고칠 수 있어요 |

## 5. 쉬운 말 사전

화면에 쓰는 말은 오른쪽 열 하나로 통일합니다. 코드 · 테이블 · 주석의 이름은 그대로 둡니다
(`machines` · `condition` · `radiusKm`).

| 어려운 말 · 내부 말 | 화면에 쓸 말 | 비고 |
|---|---|---|
| 기종 | **게임** | 보유 기종 → 있는 게임 · 기종 필터 → 게임 고르기 · 기종 변동 → 게임 들어옴·빠짐 |
| 기체 | **기계** | 기체 컨디션 → 기계 상태 · `1호기` 는 그대로 |
| 컨디션 | **상태** | 상태 3/5 · 상태 알리기 |
| 반경 | **거리** | 반경 5km → 5km 안 · 반경 전체 → 거리 제한 없음 |
| 기준점 | **기준 위치** | |
| 수렴도 | **의견 일치도** | |
| 제보하다 | **알려 주다** | 명사 `제보` 는 그대로 (실시간 제보) |
| 삭제 | **지우기** | |
| 등록(글 · 리뷰 · 댓글) | **올리기 · 남기기** | 오락실 등록(관리자)은 `오락실 추가` |
| 개인정보 수정 | **내 정보** | |
| 본인 확인 | **비밀번호 확인** | |
| 추정 | **AI가 찾은** | AI 추정 → AI가 찾은 게임 |
| 후기 | **리뷰** | 같은 것을 두 이름으로 부르지 않습니다 |
| 기종 마스터 · id · JSON · 세션 · 토큰 · API · SDK · 파싱 | (쓰지 않음) | |
| 채보 · 서열표 · 체감 난이도 · 특수패턴 · 개인차 · 미정 · 말머리 · 호기 · 익명 | 그대로 | 리듬게임 이용자가 실제로 쓰는 말 |

## 6. 예외

- **법적 문서(이용약관 · 개인정보처리방침)** — 문구 자체가 약속이라 이 지침으로 고치지 않습니다.
  바꿀 때는 시행일과 고지 절차를 따릅니다 (`app/terms` · `app/privacy`).
- **개발자만 보는 문구** — 콘솔 로그 · 서버 로그 · `.env.local` 설정 안내는 기술 용어를 써도 됩니다.
  다만 **개발 모드에서만** 보이게 하고, 운영 화면에서는 §4 의 일반 문구로 바꿔 보여 줍니다.
- **AI 에게 주는 지시문**(챗봇 · 리뷰 요약 · 기종 추정 프롬프트) — 모델이 읽는 글이라 제외합니다.
  대신 **모델이 사용자에게 쓰는 말투**는 해요체로 지시합니다 (`app/api/chat/route.ts`).
- **관리자 화면** — 같은 지침을 따릅니다. 관리자도 사람입니다.

## 7. 이 지침을 적용한 기록 (2026-09-29)

사용자에게 보이는 문구가 있는 파일 전부(컴포넌트 · 페이지 · API 라우트 · 서버 오류 클래스 · 메일)를
이 지침으로 다시 썼습니다. 남은 예외는 §6 대로 이용약관 · 개인정보처리방침과 개발용 지도 성능 패널입니다.

### 7-1. 구조를 바꾼 화면 (1화면 1행동)

| 화면 | 전 | 후 |
|---|---|---|
| 로그인 | 로그인 · 회원가입 · 취소 세 버튼이 같은 무게 + 설명 문단 | 주 버튼 `로그인하기` 하나, 가입 · 둘러보기는 글자 링크, 설명 문단 지움 |
| 가입 | 한 카드에 칸 넷 + 동의 + 버튼 셋 | **4단계** 아이디 → 이메일 → 비밀번호 → 동의. 서버가 문제 삼은 칸의 단계로 되돌아감(`field`) |
| 소셜 첫 로그인(/welcome) | 닉네임 + 선택 비밀번호 두 칸 | 닉네임 하나. 비밀번호는 내 정보에서 |
| 내 정보(/account) | 한 화면에 수정 폼 · 기기 로그아웃 · 관리자 도구 · 탈퇴 | 메뉴 → 한 가지 일. 탈퇴는 맨 아래 따로, 확인 화면이 곧 확인 단계 |
| 오락실 상세 | 버튼 이름 `대기 제보` · 옆에 "먼저 고르세요" | 고른 값이 버튼에 — `대기 3명으로 알리기` · `1호기 상태 4점으로 알리기`. 늘 보이는 게임 추가 버튼은 보조 무게 |
| 채보 상세 | `투표` · `수정` · 빨간 `투표 취소` | `0.40으로 투표하기` · `0.40으로 바꾸기`, 지우기는 글자 링크 |
| 글쓰기 | 위아래 `취소` 둘, 버튼이 이유 없이 꺼짐 | 취소는 위 글자 링크 하나, 꺼진 이유를 버튼 옆에 한 줄 |
| 파인더 | 일반 사용자에게 "등록·수정은 관리자만" | 할 수 없는 일은 보이지 않음 |
| 오류 · 없는 주소 · 오프라인 · 이메일 확인 | 버튼 여럿이 같은 무게 | 주 버튼 하나 + 글자 링크 |

### 7-2. 같이 고친 것

- **서버 오류 문구 141곳**(챗봇 라우트 제외)을 해요체 · "무슨 일 + 할 일" 로 (`lib/api-errors.ts` 공통 문구 포함).
- **검증 문구의 필드 이름 접두사 제거** — `body: 댓글을 입력해 주세요` 처럼 내부 이름이 화면에 뜨던 것 (`formatIssues`).
- **없는 기능으로 안내하던 문구 제거** — 가입 중복 이메일이 "비밀번호 찾기를 이용해 주세요" 라고 했지만 그 기능은 아직 없습니다.
- **설정 키 이름이 화면에 뜨던 곳** — AI 게임 찾기 · 리뷰 요약 · 챗봇의 `GEMINI_API_KEY` · 모델 이름, 지도 키 안내. 운영에서는 일반 문구, 원인은 서버 로그와 개발 모드에만.
- **확인 없이 지워지던 것에 확인 추가** — 내 리뷰 · 내 채보 평가 · 댓글 지우기 (평가 지우기는 실패해도 아무 말이 없던 것도).
- **브라우저 영어 문구** — 연결이 끊기면 `Failed to fetch` 가 그대로 뜨던 목록 · 제보 · 리뷰 · 서열표를 공통 문구로.
- **챗봇 말투** — 시스템 프롬프트에 해요체와 쉬운 말 사전 규칙을 넣었습니다.
- 공통 스타일 `.btn-block` · `.btn-link` · `.link-row` · `.steps` · `.account-menu` 를 더하고, 쓰이지 않게 된 `.account-section` · `.danger-zone` · `.admin-hint` 를 지웠습니다.

### 7-3. 일부러 남긴 것

- 챗봇 창에는 `보내기` · 우선순위 폼 · `파인더에서 찾기` 의 주 버튼이 함께 뜹니다. 대화 창은 차례로 쌓이는 화면이라 그대로 뒀습니다.
- 오락실 상세 · 채보 상세 패널에는 섹션(제보 폼 · 리뷰 · 투표 · 평가)마다 주 버튼이 하나씩 있습니다. 섹션을 각각의 카드로 봤습니다.
- AI 에게 주는 지시문 · 도구 설명 속의 `기종` · `컨디션` 은 모델이 읽는 글이라 두었습니다 (§6).

## 8. 점검표 — 화면 · 문구를 고친 PR 마다

- [ ] 열린 화면 · 패널 · 카드마다 `btn-primary` 가 하나다.
- [ ] 주 버튼이 `확인` · `다음` · `제출` · `등록` · `완료` 단독이 아니다.
- [ ] 새 문장이 전부 해요체다. `~합니다` 로 끝나는 사용자 문구가 없다.
- [ ] 오류 문구마다 "할 일" 이 들어 있고, `잘못된` · `올바르지 않` · `실패` 가 없다.
- [ ] §5 사전의 왼쪽 열 단어(기종 · 기체 · 컨디션 · 반경 · 수렴도)가 화면에 새로 들어가지 않았다.
- [ ] 빈 화면 · 오류 화면에 다음에 누를 것이 있다.
- [ ] 아이콘 단추에 `aria-label` 이 있다.
- [ ] 서버 오류 문구를 바꿨다면 그 문구를 대조하는 테스트도 같이 고쳤다.
